# G9103 — items assignment refused: duplicate key

Two items in one assignment produced the same key. Keyed identity is the
foundation everything else stands on — which nodes are kept, where per-item
state attaches, what selection means (the `List` round) — so a duplicate
cannot be absorbed: first-wins, drop or skip would make identity quietly
wrong.

The diagnostic shows the key and BOTH colliding items' data. There is no
fix-it: **the fix is always in the data model** — every item needs a
distinct identity. If the collection carries user-entered or external
values, key by a real ID field, not by the value itself.

The whole assignment is refused; the previous items stay live (see G9101
for the refusal doctrine — loud, wholesale, never a halt).
